## 1. 目标与非目标

### 1.1 先回答「策划在设计潜行关卡时到底在想什么」

工具必须贴合真实心理活动，否则做成「看起来专业的 demo」。潜行关卡（Hitman / 合金装备 /
Dishonored / Mark of the Ninja 一类）策划摆 NPC、画巡逻路线时反复权衡的，是下面这几件事——
本包每一项能力都对应其一：

| 策划的真实问题 | 本质 | 对应能力（本包） |
|---|---|---|
| 「从入口到目标，有没有一条全程不被看到的走法？」 | 空间可达 + 视线规避 | §3.2 相位图搜索（可行解） |
| 「哨兵**转身那一瞬间**是唯一的缝，缝有多大、几秒开一次？」 | 安全不是静态区域，而是 **(位置, 时刻)** 的函数 | §3.1 时空可见性表 · 时间轴 |
| 「走直线快但险，绕远安全但慢——我要快会死在哪，要苟要花多久？」 | 风险↔速度权衡 | §6.4 多目标 Pareto（时间 × 风险） |
| 「这个掩体只挡一个方向 / 那个是真 360° 死角，值不值得蹲？」 | 掩体质量分级 | §3.1 分层可见性（距离/视角锥/视线） |
| 「一个被发现会不会喊来同伴，把整片变红？」 | NPC 连锁反应 | §8 风险 R-1/R-2（反应态是表的预测盲区，须显式告知） |
| 「这条路线差 0.3s 就必死，对玩家是不是太苛刻？」 | 容错窗口 | §6.5 slack（每条解的最脆弱一步） |
| 「把哨兵视距 14 缩到 10，关卡是否从不可解变可解？」 | 难度参数化 | §3.1 增量重烘 + 敏感度 |
| 「玩家该走哪、我在哪给他留个能翻盘的藏身处？」 | 最佳努力部分解 | 静态设计 3（无解 Top-5 可藏点） |

用户清单里**没写、但我认为必须补**的三条高价值项，已在上表标出：**分层可见性、slack 容错、
参数化增量重烘**。潜行关卡的「手感」几乎全来自这三者，缺了就只能给「可行/不可行」的二值答案。

### 1.2 目标
- 把 A 包的 NPC 巡逻与视野，**烘焙成一张可离线消费的时空可见性表**（本包唯一数据真源）。
- 在**编辑态（非 Play）**用可拖动时间轴展示：每个 NPC 各时刻的位置、危险区、安全区、玩家可达区。
- 求解「≤N 个相位内能否抵达撤离点」的可行解；有解给前 M 条、无解给启发式 Top-K 可藏点。
- 导出/注入玩家路点数据集，并驱动**引擎实跑**验证每条数据集的真实可行性（含反应态）。
- 按给定玩家动线**反推 NPC 巡逻路点**，落到场景副本。
- 全程 **编辑器 / 引擎双端友好**：算法与数据在 Runtime，面板与烘焙调度在 Editor。

### 1.3 非目标（明确不做，防蔓延）
- **不做**玩法逻辑本体（视野判定、状态机、察觉累积全归 A 包）。B 只**消费** A 的判定结果。
- **不自建**第二套可见性算法。一切「能不能看到」的口径必须来自 A 的 `IVisionWorld`（§4）。
- **不替代**实跑仿真。表的预测是「纯巡逻相位」假设，最终可行性仍以引擎实跑为准（§3.3）。
- **不做**运行时 AI 导演/动态难度（表可供其使用，但属未来、不在本包）。
- **不碰**共享文件除非走评审申报（`Packages/manifest.json` 等；UMPM 并行若要引入须先申报）。

## 2. 约束

- **Unity 6（6000.6.7f1）**；依赖方向严格 `B → core`，**B 的 asmdef 禁止引用 A**（§5 方案 P，
  由 `Tools/verify_project.py` 的 `dep-direction` 强制，`validateReferences` 不得关）。
- **A 缺席优雅降级**：`Services.TryGet<IPatrolWorld>()` 失败时面板显示「未接入玩法包」，不抛异常。
- **线程约束（决定架构，非可选项）**：A 的 `CanSeeAt → VisionGeometry.Evaluate(..., RaycastClear)`
  底层是 `Physics.RaycastNonAlloc`——**Unity 物理查询只能主线程**。因此「射线判定」不能后台并行；
  本包用「主线程烘一次 → 冻结成表 → 之后纯 CPU 查表」绕开（见 D-01）。
- **确定性**：同输入必得同输出（表、搜索、反推皆然）。并行归约的顺序、浮点累加次序都要固定，
  否则策划每次烘结果不同就不可信。
- **预算（初值，实现阶段用基准实测校准，非结论）**：单场景烘焙目标 < 30s 首烘、< 1s 增量重烘；
  表资产 < 4MB；见 §7。

## 3. 方案概述

### 3.1 核心抽象：时空可见性查找表（Spatio-Temporal Visibility Table）

**这是全包的地基，其余功能都是它的消费方。**

- **空间**：把可活动区离散成网格（可活动 footprint，非整矩形——先剔除墙/掩体内与地图外的格）。
- **时间**：关键优化——**不存全局 LCM 周期**。每个 NPC 的「某格在某时刻是否可见」是**该 NPC 自身
  巡逻周期 c_i 的纯函数**（A 的位姿本就是 t 纯函数）。故表**按 NPC 分片**，第 i 片只需覆盖
  `[0, c_i)`、时间桶 `Δt`。查全局某格在时刻 t 是否安全 = 对所有 NPC 取 `t mod c_i` 查各自片做
  AND。**表体积从 `格 × (LCM/Δt)` 降到 `Σᵢ 格 × (c_i/Δt)`**，且天然增量（改一个 NPC 只重烘一片）。
- **每格每片存什么**：三层可见性掩码（对齐 `StealthQueryLayers`）——
  `DistanceOnly`（进射程）/ `Cone`（进视角锥）/ `LineOfSight`（真的无遮挡看到）。策划要看的是
  LOS 那一层的**时间开合**，但保留下两层用于「险到什么程度」的分级着色。
- **烘焙即 A 的判定**：烘表时逐 (格心, 时刻) 调 `IVisionWorld.CanSeeAt(actorId, t, cell, Full)`，
  **不复制任何判定代码**（§4 红线）。表因此与运行期同源，「表说安全」=「那一刻真看不到」。

产物 = 一个 `ScriptableObject`（表头：格坐标原点/尺寸/Δt/各 NPC 的 c_i；体：分片位图）+
派生的**静态层**（永久安全格、永久禁区格）与**临界格表**（仅部分时间危险、才需展开时间维）。

### 3.2 静态设计流水线（对应静态 1~4）

```
A 契约(PoseAt/CanSeeAt/…)
      │  ①主线程分帧烘焙（进度条、可中断、改参数只增量重烘）
      ▼
  时空可见性表  ──► 时间轴 UI（拖 t：NPC 位置 + 危险/安全/可达区同源着色）   [静态1]
      │
      │  ②相位图搜索（A* + 剪枝，见 §6）
      ├──► 有解：前 M 条 (到达时间, 路点, slack) ─► 弹窗确认 ─► 导出数据集 ─► 注入动态1  [静态4]
      └──► 无解：Top-K 可藏点 (距撤离点启发排序 + 最早安全到达时间)                    [静态3]
```

- **时间轴（静态1）**：横轴 `[0, 宏观相位窗]`，可拖；每个 NPC 一条「相位泳道」显示位置；
  主视图叠加当前 t 的危险/安全/可达热区（全部查表渲染，不现算射线）。玩家可达区从「上一轴节点
  的安全集」按移动速度扩张得到（用户的「基于上一个轴节点的安全区域」= 时变可达性传播）。
- **可行解判定（静态2）**：时间扩展图上的 earliest-arrival 搜索，N（相位上限）可配置。剪枝见 §6。
- **无解回退（静态3）**：搜索耗尽仍不达目标 → 从 Dijkstra 距离场取 (风险低, 离撤离点近) 的 Top-K。
- **有解导出（静态4）**：k-shortest（§6.3）取前 M；弹窗（Editor 侧）确认后写成 JSON 路点数据集。

### 3.3 动态设计流水线（对应动态 1~3）

```
玩家路点数据集（用户手配 或 静态4 注入）              [动态1]
      │  ②实跑验证：引擎内沿数据集推进、真跑 A 逻辑（含反应态/遮挡/通报）
      ├──► 单窗口顺序实跑（MVP，零新依赖）
      └──► 多窗口并行（进阶，需 UMPM，见 D-08 + 评审申报）              [动态2]
      │  ③反推 NPC：给定期望动线，局部搜索 NPC 路点 → 局部重烘 → 评估「戏剧张力」
      └──► 写入【场景副本】（禁破坏性覆盖当前场景，见 D-09）             [动态3]
```

- **实跑 vs 查表的分工（关键洞察）**：表是「NPC 严格按巡逻相位、不进入反应态」的**静态假设**；
  实跑能验证含 Alerted/Searching/同伴通报的**完整逻辑**。两者结论不一致时以实跑为准——**而差异本身
  就是给策划的信号**（「表预测安全，但该 NPC 被惊动后会绕路堵你，实际不安全」）。这是补用户清单的
  又一高价值点：把「预测与实况的差」做成可见的诊断。
- **并行实跑的现实约束**：同一 Editor 实例开多 Play 并行为本环境不可行（实测：失焦不推进帧、
  多 AI 共享单实例）。正解是 **Unity Multiplayer Play Mode**（每窗口独立 domain，静态
  `Services`/`StealthClock` 在各自域内独立，反而适配并行仿真）。故 MVP 先做**单窗口顺序实跑**，
  并行作为需评审申报的进阶（D-08），并发数=窗口数受核数限制、可配置。

### 3.4 Runtime / Editor 切分（双端友好的落点，AGENTS §0.1.3）

| 组件 | 归属 | 引擎运行态能否复用 |
|---|---|---|
| 表数据结构 + 查表 API（`VisibilityTable`、分层掩码、per-NPC 片） | **Runtime** | ✅ 打包后只读消费 |
| 相位图节点/边模型、A*/Dijkstra/Yen、剪枝与支配判定 | **Runtime** | ✅ 可做「运行时提示/复盘回放」 |
| 玩家路点数据集 schema、复现器（沿数据集推进的确定性步） | **Runtime** | ✅ |
| `ISafeIslandProvider` 实现（安全岛 `Contains`） | **Runtime**（经 core 反向注入 A） | ✅ A 运行期查询 |
| 烘焙调度（主线程射线循环、分帧、进度、增量失效订阅） | **Editor** | —（依赖 A 的物理判定，本就主线程） |
| 时间轴窗口、热区渲染/Gizmos、导出弹窗、场景副本生成、UMPM 编排 | **Editor** | — |

`runtime-purity` 校验器强制 Runtime 不引 UnityEditor；表与算法进 Runtime 才谈得上「引擎侧无需重复配置」。

### 3.5 关键实现选择（一句话理由）
- 位姿/可见性**一律经 core 契约现取**，B 不缓存 A 的内部对象类型（防方案 P 失效）。
- 表**按 NPC 分片 + 用 t mod c_i**，避免 LCM 爆炸、天然增量（见 §3.1）。
- 搜索是**纯 CPU 查表**——所以能后台、能并行、能引擎复用；射线只在烘焙阶段主线程跑一次。
- 实跑**真调 A 的判定**（引擎物理世界真跑），预测与实况互为校验，不追求「查表代替实跑」。

## 4. 跨包接口（B 只经 `com.collin.core` 的 `Collin.Core.Stealth` 契约）

**消费方（A 注册实现，B 取用；取不到即降级）：**
- `IPatrolWorld`：`PoseAt`/`TryPoseAtWorld`（时间轴 NPC 位置）、`BuildTrajectory`（轨迹绘制，
  **禁止 B 自算折线**，同源要求）、`TryGetWaypoints` + `TrySetWaypoint`/`TrySetRouteTuning`
  （动态3 反推路点的写回落点）、`MaxCycleTime`/`ClockState`。
- `IVisionWorld`：`CanSee`/`CanSeeAt`/`CountSeers`——**B 一切可见性判定的唯一来源**，分层用
  `StealthQueryLayers`。
- `IDetectionWorld`：`SuspicionOf`/`StageOf`/`ResetAll`（实跑复现时读察觉演化）。
- `IStealthScrubDriver`：`ScrubTo`/`ResumeAuto`/`IsManual`/`Changed`（编辑态时间轴驱动 NPC 位姿，
  与危险/热区**同源同步**，否则两套时间）。

**实现方（方向相反，B 提供、A 消费）：**
- `ISafeIslandProvider`（`Count`/`TryGetBounds`/`Contains`）：B 依表算出「安全岛」并注册进
  `Services`；A 在判定 L4 遮蔽修正时查询「玩家此刻是否在岛内」。**A 未取到服务须按「无安全岛」降级。**

**事件通道（core 具体子类）：**
- 订阅 `StealthWorldChangedChannel`（路点/单位/视野/安全岛变更）→ B 侧**作废并增量重烘**。
- 订阅 `StealthTimeIndexChannel` / `DetectedChannel` → 时间轴对齐 t、把察觉事件钉回时间轴。

红线：B 的 Runtime/Editor 源码里**只允许出现 `Collin.Core.Stealth` 的类型**，出现任何 A 包具体类型
即破方案 P（stealth DESIGN §4.3 明列此约束，`verify_project.py` 的 `dep-direction` 守）。

## 5. 决策记录

| 编号 | 决策 | 备选 | 理由（含对用户条目的对应） |
|---|---|---|---|
| **D-01** | 主线程射线**烘焙成表一次**，之后求解/可视化全走纯 CPU 查表 | ①每次现算射线 ②B 复制一套判定 | 物理查询仅主线程（实测），①无法后台/并行且每次重算极慢；②两套口径必漂移。查表可并行、可引擎复用、与 A 同源。|
| **D-02** | 表**按 NPC 分片、用 `t mod c_i` 索引**，不物化全局 LCM 周期 | 全局 LCM 时间轴一张表 | 位姿是各 NPC 自身周期纯函数；LCM 随 NPC 数爆炸，分片把体积降到 Σ、且天然增量。|
| **D-03** | 可行解 = **时间扩展图 A\***（earliest-arrival），启发=空间最短距离÷最大速度 | 朴素 DFS / 全枚举 | 用户静态2 点名要剪枝降复杂度；可采纳空间启发 + §6 四道剪枝把指数降为多项式。|
| **D-04** | 无解走 **Dijkstra 距离场 + (风险,距撤离点) 排序取 Top-K** | 直接报「无解」了事 | 用户静态3 要「最近撤离点 5 位置 + 最早到达时间」；即 A* 失败的最佳努力部分解。|
| **D-05** | 前 M 条解用 **带禁止边的迭代 A\*（Yen 简化）** + 每条附 **slack** | 只给 1 条最优 | 用户静态4 要前 M 短解；slack（最脆弱一步的容差）补「对玩家是否过苛刻」判断。|
| **D-06** | 实跑**真调 A 引擎逻辑**（含反应态），预测/实况差异作诊断 | 用表直接判可行性 | 用户动态2 要「实跑验证可行性」；表是静态假设，实跑才含连锁反应，差异是高价值信号。|
| **D-07** | 数据集 = **JSON schema + ScriptableObject 双形态** | 单一格式 | 手配（SO 进 Inspector）与静态4 注入（JSON 可 diff/版本化）两路都要（用户动态1）。|
| **D-08** | 并行实跑：MVP 单窗口顺序；多窗口走 **UMPM**，需申报评审 | 同实例硬开多 Play | 本环境同实例多 Play 不可行（实测失焦不推帧）；UMPM 每域独立、静态服务天然隔离。并发数可配置=窗口数。**已拍板**（⇒ D-15）：多窗口纳入后续迭代，不提前实现。|
| **D-09** | 反推 NPC 用**基于局部重烘的坐标下降/局部搜索**，结果写**场景副本** | 全局重烘 / 覆盖当前场景 | 路点坐标连续无闭式解；只局部重烘受影响格控成本。副本避免破坏现场（工程教训：禁独占新建/覆盖他会话现场）。|
| **D-10** | 安全岛 B 实现、A 消费（反向注入），B 不碰 A 内部 | B 把安全岛塞进 A | §5 方案 P 已定；`ISafeIslandProvider` 正是为此预置。A 缺席须降级。|
| **D-11** | 烘焙**分帧 + 进度 + 可中断 + 订阅失效增量** | 一次性同步阻塞烘完 | 编辑器不能卡死（工程教训：禁模态阻塞指令通道）；改参数增量重烘是性能命门。|
| **D-12** | 短名定 `com.collin.stealthplanner`（用户 2026-11-05 拍板） | `stealthdesigner` / `stealthaid` | 「planner」直指本包核心价值=求解/规划（静态2/3/4 + 动态3），比「designer/aid」更贴语义；已落地的目录与 asmdef 无需迁移。|

## 6. 算法专章（静态/动态核心，用户点名要）

### 6.1 时间扩展图
节点 `(cell, tBucket)`；边 = 移动到邻格耗时 `cellSize / speed`（跨若干 Δt）。约束：整条边的
经过时刻（插值）都不得处于 LOS 危险（查表）。目标 = 撤离格、代价 = 到达时刻 → earliest-arrival。
**相位封顶**：时间维只需 `[0, 宏观相位窗)`，超出用各 NPC 的 mod 复用表——**N 只增搜索轮数、
不增表大小**（D-02 红利）。

### 6.2 四道剪枝（用户「剪枝降复杂度」）
1. **永久格合并**：所有时间都安全→「随时可过」不展开时间维；所有时间都危险→移出图。
   只有**临界格**进时间扩展。潜行掩体多，临界格通常仅占少数，直接砍掉绝大部分节点。
2. **A\* 可采纳启发**：`h(cell)=网格最短距离/speed_max`（忽略时间/可见性的空间下界，保最优性）。
3. **支配剪枝（Pareto dominance）**：同格上，到达更早 **且** 累积风险不更高的解支配后来者，丢弃。
4. **相位对齐去冗余**：同一格在同一 NPC 相位下的重复访问用 mod 归并。

### 6.3 k-shortest（D-05）
在时变图上跑 **Yen / 带禁止边的迭代 A\***：第 1 条最优解 → 逐次「禁止一条边重搜」产出第 2..M 条。
复杂度 `O(M·|V|·(|E|+|V|log|V|))`，故 **M 默认小（3~5）**、可配上限。

### 6.4 多目标（时间 × 风险，补充拓展）
可选把「最短时间」与「最小暴露（累计 LOS×时长）」做成 Pareto 前沿，让策划看「多花 3s 换少 40%
暴露值」的取舍，而非单一标度。

### 6.5 slack（容错窗口，补充拓展）
每条解的每一步记录「距被抓还差多少秒 / 视角还差多少度」，取全局最小 = 该解最脆弱一步。
无 slack 的最短解对玩家可能不可能完成——这项直接决定关卡「公不公平」。

### 6.6 反推 NPC 路点（动态3）
目标函数 `张力 = f(玩家动线的险情次数, 安全裕度)`。迭代：扰动某 NPC 路点 → **只局部重烘其影响格**
（用新 c_i 与位姿）→ 评估张力 → 坐标下降/模拟退火接受。输出写回 `TrySetWaypoint`（先落场景副本）。
连续优化无闭式解，靠局部重烘控成本 + 迭代上限兜底。

### 6.7 建议参考相位时长（决议 D-13 的实现口径）

用途：给用户一个**填 P 的参考值**，不自动改写手配值。

- 输入：各 NPC 周期 `c_i`（来自 `IPatrolWorld.Actors[i].cycleTime`）。
- 做法：把周期**量化到 Δt 栅格**再求整数最小公倍数，避免实数 LCM 无解：
  `k_i = max(1, round(c_i / Δt))` → `L = lcm(k_1..k_n)` → **参考时长 = `L × Δt`**。
- 兜底（必须实现）：`L` 会随周期互质而爆炸（如 23 与 29 → 667 个桶）。
  设 `L_max`（默认 7200 桶 = Δt 0.5s 下的 1 小时）；超限时**退回 `max(c_i) × 2`** 并给 Warning：
  「严格相位对齐周期过大，此为近似值；本工具按 mod 分片工作，P 不取 LCM 不影响结果正确性，
  只影响『重复模式』的展示长度」。
- **正确性声明（须写进面板文案）**：P 取多大**不改变**「是否存在 ≤N 相位的可行解」——
  可见性按各 NPC 自身周期取模查询（D-02）。P 只决定时间轴与搜索展开的时间维长度。
  这条必须显式告知，否则策划会误以为「相位窗设小会漏解」；真正决定是否漏解的是 **N（相位轮数）**。

### 6.8 参数敏感性（决议 D-16 的配套）

面板改格长 / Δt / P 时**实时预览估算**（不做完整重烘）：
`活动格数 ≈ footprint面积 / 格长²`，`时间桶数 ≈ P / Δt`，
`表体积 ≈ 格数 × Σ⌈c_i/Δt⌉ × 掩码位宽`。
超预算阈值（§7）时把「开始烘焙」按钮标警示色并提示调参，避免用户盲烘出分钟级卡顿。

### 6.9 相位可达传播（M2；M3 求解器的地基）

入口 `PhaseReachability.Compute(table, startCell, buckets, stepCells, out failure)`，
返回 `Field`（逐桶可达位图 + 每格最早到达秒 + 整窗并集）。纯 CPU、只查表、不碰物理（D-01）。

- **推进规则**：按桶 BFS。桶 `b` 的可达集合由桶 `b` 的可达格向桶 `b+1` 扩散，
  每格可走 `stepCells` 格（欧氏半径），也可原地等待（等待只查**下一桶**是否安全——见 D-18③）。
- **中间格判据**：一步跨多格时，**严格中间格**必须在**本桶**安全（整数超行栅格化逐格检查，
  只查起止格会一步跳过掩体，M2 实测踩过）；**终点只查下一桶**（D-18②，保「等哨兵转身再进掩体」）。
- **步长口径**：`stepCells = floor(v × Δt / 格长)`，**允许为 0**（只能等待；兜底成 1 等于虚构移动力）。
- **三处危险合成**：每桶判据 = 表危险（`BuildDangerMask`）**或** 无数据格（`BuildNoDataMask`，D-19）。
  热区渲染吃同一份合成掩码 ⇒ 面板绝不会把墙画成绿色可走。
- **失败即空场**：出发格 t=0 已被看见 / 参数非法 ⇒ 返回空 `Field` 并带中文原因，不给半张可用的场。

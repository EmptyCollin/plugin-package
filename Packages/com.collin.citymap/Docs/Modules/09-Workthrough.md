# Modules/09 — 操作序列推演（设计验证）

> 目的：用一条真实工作流把 00~08 的规则跑一遍，验证是否自洽、可执行、可反悔。

> 结论：**发现 9 处空洞（4 处阻断级）**，本文件给出裁决方案；已回写进 01/03/04/05/07/08 与总纲。

## 1. 推演序列（Rundeck 主线）

前置：Route 1 已走完 A1 新建城（seed=1700, worldSize=2000, urbanFlatness=0.25）、
A2 放一个 CBD 金融场（type=Finance, inner=60m, outer=380m, innerValue=85, outerValue=0, 曲线 EaseOut）。
下面依次执行：**T1 画河 → T2 拉高 ρ → T3 删掉一条穿院子的主干道 → T4 把城心场域往东挪 120m**，
并在 T3 前做一次 T0=框选 CBD 街区锁区（因为用户会锁区，这条路径必须验证）。

### T1 画一条主干河（左键拖，穿过 CBD 南侧，终点落在城东南）

| 维度 | 推演结果 | 依据 |
|---|---|---|
| 提交动作 | RiverBrush Commit | 02 §5.1 |
| 拖拽期 | 只算吸附与河带 overlay，无 GameObject、无资产写盘 | 02 D-02-7 |
| 脏集合 | S2 → S1a?（不重跑基底，只重放下切层）→ S1b（约束变）→ S3（桥位）→ S4（水缓冲切边）→ S5（临水派生场）→ S6（脏 parcel） | 总纲 §3.2、02 §4 |
| 拓扑 | 终点在坡上 → 沿 D8 补下游到城界，补的段标 `role=Auto`，**须用户确认**（不静默改线） | 02 D-02-5 |
| 固化对象 | 此刻还没有 adopted 对象，无冲突 | — |
| 反悔 | L1：一笔=1 条 undo（河线 + 下切层同时回滚）；无锁区参与 | 02 §5.2、08 §5 |

**推演成立**。附带发现 1 个含糊点（见 §3 H-8）：河把 CBD 地块切成南北两半，切出来的小地块若 < `minParcelArea` 会被标 Invalid，
CBD 里就出现一块"既不能建也长不出路"的废地 → 需要规则：细分/水切产生的过小块**默认并入相邻地块**而不是留空（H-8）。

### T2 把 ρ 从 0.16 拉到 0.22

| 维度 | 推演结果 | 依据 |
|---|---|---|
| 拖滑杆（Preview） | 沿最大堆继续分裂 k 步，只更新边集合与 ρ 读数，不建 GameObject，单步 ≤30ms | 03 §4.6 |
| 松手（Commit） | 派生层全量重建 + 标脏 S4/S5(可达场)/S6 | 03 §4.6 |
| 固化对象 | 尚无 → 但**已放场域的内径平台范围**会被新支路切穿：合法（场域是 Model 语义，不是几何占位） | 05 §1 |
| 反悔 | L1：一次滑杆会话 = 1 条 undo；回退=弹栈，回到 0.16 的边集合应完全一致 | 03 A-3-2 |

**推演不成立（H-1，阻断级）**：A-3-2 的"完全一致"只在**期间没有其它意图变化**时成立。
弹栈的前提是分裂栈有效；一旦中途挂过负约束/锁区/adopt（新墙），栈与当前 pinned 图不一致，回退会回到"旧墙世界"。
→ 修订：**意图层任何墙集合变化 ⇒ 分裂栈作废、按当前 pinned 图确定性重建**；A-3-2 加限定条件。

### T3a 先锁区：框选 CBD 南侧一个街区（含 6 栋自动建筑、2 条自动路边）

| 维度 | 推演结果 | 依据 |
|---|---|---|
| 提交 | `LockRegion` 对象进人工层；区内自动路边/建筑批量 adopt；外接框生成 boundary wall | 08 §4.2 |
| 下游 | S3 细分跳过区内；S5/S6 不再重排区内；区外细分把墙当已有边 | 08 §4.2 |
| 反悔 | L1（1 条 journal）/ L2 整条回滚；解锁前列出将丢弃 N 栋 | 08 §4.2、§5 |

**推演暴露 H-2（阻断级）**：08 §4.2 只说"S3/S4 跳过区内"，**没有说 adopt 的对象对 S2/S3 是否构成几何禁入**。
后果：锁区后紧接着 T2 若再拉高 ρ，自动支路可以从**两栋 adopted 建筑中间穿过去**（建筑本身不挡细分，因为细分只看墙）
→ 固化建筑被新路压住 → A-8 违规、用户"我确认过的东西被毁了"，这是本工具最恶性 bug 的一种。
→ 修订：**adopt 的完整语义 = 对象 footprint 注入"硬占用"禁入集合**（S2 河道、S3 细分、S6 建筑都视为墙）；
`OccupiedHard` 进掩码（见 H-3）。

### T3b 删掉一条"穿院子的"Arterial 主干道

这里必须分两种情况推，因为用户在 UI 里看不出这条是人工画还是程序长的。

**情况 B1：它是人工画的 pinned Arterial（大概率，因为主干道人一般会亲手画）**

| 维度 | 推演结果 | 依据 |
|---|---|---|
| 提交 | 真删除（意图对象消失），Ctrl+Z 找回 | 08 §4.3 |
| 脏集合 | S3（边消失）→ S4：**两侧地块合并成一个大块** → S5（地块级 dominant 重算）→ S6（原沿街 slot 全消失，新地块重排建筑） | 04 §3.1、08 §3.4 |
| 固化对象 | 原沿街 adopted 建筑的 **slot 没了** → 未定义 | — |
| 反悔 | L1 删除；L4 检查点恢复 | — |

**推演暴露 H-4（阻断级）**：`adopted` 建筑是"场景 GameObject + slotId 引用"，而 slotId 是派生几何哈希。
上游一变（删路/改 ρ/改河/区域回滚）slot 就消失，adopted 对象**失去宿主**，文档完全没写怎么办：
若不处理 → 恢复时要么凭空删掉用户的固化楼（恶性），要么留下"无 slot 的孤儿楼"但 diff 不认识它（下次重排被吞）。
→ 修订：定义 **orphan（自由固化对象）** 状态：`slotId` 失效 → `orphan=true`，保留 Transform 与行 id，
仍进 `OccupiedHard` 禁入集合；S6 重排时把它当"已占位的人工建筑"参与冲突检测；
提供「吸附到最近合法 slot / 原地保留 / 删除」三选一提示条目（info 级，不打断）。

**情况 B2：它是自动生成的 Collector/Local**

| 维度 | 推演结果 | 依据 |
|---|---|---|
| 提交 | `Del` → 挂 `NoRoad(红线走廊)`，toast 说明；重生成不再出现 | 08 §4.3 |
| 连锁 | 走廊变空地 → 地块合并 → **原地长出建筑**（多半不是用户想要的"院子"） | 04 §3.1 |

**推演暴露 H-5（体验级）**：删自动路后原路址默认可建，与用户"我要那块院子"的直觉冲突。
→ 修订：删除自动路时**默认转 `NoRoad` + 可选 `NoBuild`**，交互上给一条 toast 内联选项：
`[仅禁路(默认)] [禁路且留白] [转为人工路(adopt)]`，并把选择记进 journal（可撤销、可改）。

### T4 把城心场域往东挪 120m

| 维度 | 推演结果 | 依据 |
|---|---|---|
| 拖拽期 | 只重烘脏圆环 + overlay，禁碰 GameObject | 05 D-05-6 |
| 松手 Commit | S5（脏环）→ S6（脏 parcel 重排） | 总纲 §3.2 |
| 固化对象 | 锁区内的 CBD 建筑不动 → 城市形态滞后（见 H-6） | — |

**推演暴露 H-7（阻断级）**：01 §4.4 `deriveUrbanCenter` 让 **S1a 的压幅中心、07 §3.2 的高度衰减中心**实时取金融场域位置。
于是"往东挪 120m"不再只是 S5/S6 局部脏，而是：城心变 → `urbanFlatness` 衰减中心变 → **S1a 全城高度重算**
→ 约束变 → 地块几何变 → parcel id 变（几何哈希）→ 全城建筑被判定"变了"重排 → 还连带把 D8 水系、道路纵坡全推翻。
一次"拖动场域"的手势引发全城重算，既摧毁手感（05 A-5-5「拖拽期无 GameObject」形同虚设），也摧毁局部稳定性（00 D-10）。
→ 修订：**城心降格为独立意图对象 `CityCenterAnchor`**（进 `CityProject`，持久化、可撤销）：
- S1a 压幅中心、`distanceDecay` 中心**只读锚点，不实时读场域位置**；
- 场域面板提供按钮「设为城心」= 一次显式提交，把锚点写为该场域当前中心；
- 锚点变更属于**高危操作**（影响地形与全城形态）→ 触发 §6.2 影响预览 + 自动快照；
- 来源必须可见：面板黄字"城心来自锚点（可追溯到 场域 CBD 于 v37 设置）"。

**H-6（体验级，非阻断）**：城心/门槛往东移后，西部原金融区门槛降低，但锁区/adopt 的 6 栋金融塔楼仍在原地
→ 出现"金融区已移走、高楼还留着"。这是 adopt 的正确结果，但必须让用户明白它不是 bug：
→ 修订：条目分级 `error / warning / info`；新增 info 型条目"形态滞后"：列出"该处门槛已降至 20，但保留 6 栋固化金融建筑（锁区 X）"，可点击定位、可一键解锁重排。

## 2. 逐层反悔能力复核（沿 T1→T4 反向回退）

| 目标 | 路径 | 可行性 |
|---|---|---|
| 只想把场域挪回原位 | Ctrl+Z（L1，一次拖动=1 记录） | ✅（H-7 修订后为纯 S5/S6 局部） |
| 撤销"删掉的主干道" | Ctrl+Z（L1 恢复意图对象）→ Tracker 版本 bump → S3~S6 重算 | ⚠️ 依赖 H-9（Tracker 集合哈希），否则可能漏检 |
| 撤销"锁区" | 历史面板解锁（列出丢弃 6 栋）或 L2 journal 整条回滚 | ✅ |
| 撤销"ρ 拉高" | Ctrl+Z 回滑杆值 → 分裂栈重建（H-1 修订） | ✅ 修订后 |
| 撤销"整条河" | Ctrl+Z（一笔）；若已跨会话 → L4 检查点/区域恢复 | ✅；恢复区域时跨界河线**不裁剪**（08 D-08-7） |
| 撤销 T3a 之后所有改动，但保住 T4 的新场域位置 | L3 区域恢复 + 场域在选区外 → 保留 | ✅ 前提是 parcel 局部稳定（04 A-4-4 的 95% 口径） |

**H-9（实现级，必须写进 08）**：`UndoHistoryTracker` 若只比对 `manualVersion`，会漏两类变化：
① **undo 恢复一个被删对象**时，其恢复后的版本可能等于派生层记忆值 → 差异为空 → 不重算（画面停在"没有这条路"）；
② **移动 adopted 建筑的 Transform** 不应触发全城重算，只需更新禁入集合。
→ 修订：Tracker 每帧比对 = `意图对象集合哈希(id 集 + 数量)` **异或** `逐对象版本差`，且 bump 映射到脏位需按对象类型分派
（场域→Field；河线→River；pinned 边→Road；锁区/负约束/adopt→Occupied+对应下游；adopted 建筑 Transform→仅 OccupiedHard）。
需要一张「对象类型 × 变化 → 脏集合」映射表（已写入 08 §5.1 附表）。

## 3. 空洞清单与裁决（按严重度）

| 编号 | 空洞 | 严重度 | 裁决（回写位置） |
|---|---|---|---|
| **H-7** | 场域位置被当作 S1a 城心与 07 高度衰减的实时真源 → 一次拖动=全城重算，局部稳定性崩塌 | **阻断** | 城心降格为独立意图锚点 `CityCenterAnchor`；场域→「设为城心」显式提交；变更算高危（01 §4.4、07 §3.2、08 §6.2、00 §6） |
| **H-2** | adopt 的对象不挡 S2/S3 的几何生长 → 自动路/河可穿过固化建筑 | **阻断** | adopt 语义 = footprint 进 `OccupiedHard` 硬占用禁入集合，S2 河道/S3 细分/S4 地块/S6 落位全部视为墙（08 §4.1、00 §2.4） |
| **H-4** | slot 是派生几何哈希，上游变化使 adopted 建筑失去宿主，行为未定义 | **阻断** | 新增 orphan 状态：保留对象 + `orphan=true` + 仍进禁入集合；info 条目给三选一处置（07 §5、08 §3.4） |
| **H-1** | 分裂栈"弹栈可逆"与墙集合变化冲突，A-3-2 断言条件缺失 | **阻断** | 墙集合变化 ⇒ 栈作废、确定性重建；A-3-2 加"期间无墙变化"限定（03 §4.6、03 §8） |
| **H-9** | Tracker 仅比 `manualVersion` 会漏"恢复被删对象"；移动 adopted 楼会误触发全城重算 | 实现级 | 集合哈希 + 版本差双检；对象类型→脏位映射表（08 §5.1） |
| **H-3** | 负约束/adopt 占用要参与每格判定，但掩码 8 位已用尽 | 实现级 | 掩码升 `ushort`，新增 `OccupiedHard/NoRoad/NoBuild/NoWater/Interior`；负约束烘焙进掩码（00 §2.4、08 §8） |
| H-5 | 删自动路后原路址默认可建，与"我要院子"的直觉冲突 | 体验级 | `Del` 时内联三选一（仅禁路/禁路且留白/转人工路），默认仅禁路并说明后果（08 §4.3） |
| H-8 | 河/细分切出的过小块变废地（不能建也长不出路） | 体验级 | 过小块默认**并入最大邻块**（记录并入关系），连续两次仍过小才标 Invalid（04 §3.1） |
| H-6 | 门槛移动后固化建筑造成"形态滞后"，用户误判为 bug | 体验级 | 条目三级 `error/warning/info`，新增 info"形态滞后"（08 §3.4、§6.1） |

**新规则补入冲突矩阵（08 §3.4）**：新增两列/行——
① 上游提交 × **orphan 对象**：保留 + 提示，永不自动删；
② **删除 pinned 人工层对象**（此前矩阵缺行）：必弹影响预览（爆炸半径大），并列出将产生的 orphan 清单。

**掩码位规划（00 §2.4 重写）**：`ushort`，`Buildable/Water/WaterBuffer/Road/Parcel/ManualLocked/OutOfBounds` 保留，
新增 `OccupiedHard(adopt 或手刷占用)`、`NoRoad`、`NoBuild`、`NoWater`、`Interior(过大地块内部不产 slot)`。

## 4. 结论与下一步

- 主线序列 T1→T4 在修订后**可执行、可反悔、局部稳定**：
  T1/T2/T4 均为局部脏（T4 修 H-7 后只脏 S5/S6），T3b-B1 是唯一的全局性操作（删骨架路→地块合并），
  已由"必弹影响预览 + 先锁定"覆盖；反悔四层全程可用。
- 推演价值集中在 H-1/H-2/H-4/H-7：**四条都是"文档各自自洽、跨模块组合后失效"**，正是纯分模块设计最容易漏的那类。
  教训固化：跨模块交互（顺序/反悔/占用）必须有 08 这样的横切文档，并靠 09 这种推演来验证。
- 后续（设计完备再动手，按用户要求）：
  1. 建议追加推演轮次：R2「Route2 一键造城后回头重画河并改表」、R3「跨会话：重启编辑器 + 域重载后继续 T3-T4」、
     R4「与另一 AI 并行改 stretch/core 时的桥接装配时序」；
  2. M0 开工前置条件：H-1~H-9 全部回写完毕（本文件即修订依据）；
  3. ADR-0001（core 加 `IStretchService`）在 M9 前定稿签名。

## 5. R2 —— Route2「一键造城」后回头改

前置：用户什么都不画，直接点「一键造城」（默认参数 → S0~S6 全跑）。产物：全城 auto 路 + 约 9000 栋 auto 建筑，**意图层为空**。
随后执行：R2-a 重画一条河穿城中心；R2-b 把表里第 12 行（某栋塔楼）删掉；R2-c 再点一次「一键造城」。

| 步骤 | 推演结果 | 判定 |
|---|---|---|
| R2-a 画河 | 河为人工层，参与重放第 2 步；S2→S3(桥)→S4→S5→S6 重排；沿途 auto 建筑被推开/消失 | ✅ 合法，但见 **H-14** |
| R2-b 删表行 12 | 08 矩阵只写"tag 指向消失→记条目，不删物体"。可那 30 栋实例：`rowId` 指向已不存在的行、`adopted=false` | ❌ **H-15 阻断** |
| R2-c 再造城 | 与首次同 seed 同结果（确定性）；R2-a 画的河**被保留**（人工层不被摧毁，D-08） | ⚠️ **H-16 语义冲突** |

### H-14（体验级）Route2 后满城 auto，用户却当成"已成事实"
R1 修订后 adopt 才是硬墙，而 Route2 产物一个都没 adopt → 用户随手画条河，9000 栋里被推开几百栋，
用户主观感受是"我造好的城被改了"（尽管客观上他从未确认过任何一栋）。
**裁决**：`一键造城` 完成后弹一条**非阻断 info + 显式动作**：
「本次生成 9123 栋建筑、412 条路，当前 **0 个固化对象**——后续改动将自由重排全城。 [冻结全城]」
`冻结全城` = 一次性 `LockRegion(全图)`（= 用户真正想要的"保住现状再继续改"）。
补进 08 §4.4 口诀表新增一行「保住整城现状 → 冻结全城」，与"锁区"并列。

### H-15（**阻断级**）删表行使已存在实例成为"无主 auto 物"
是 H-4 的同类变种，R1 漏了：**slot 会消失，表行也会消失**。
这 30 栋实例：a) 不被 S6 diff 认领（diff 按 rowId，行没了）；b) `adopted=false` → 不在"不可替换"集合；
c) 不占 `OccupiedHard`（非 adopt）→ 新建筑可以叠上去 → **直接违反 A-8，且每次重生成越积越多**。
**裁决**：删除 `BuildingProfile` 行时，按 §4.1 的处置规则执行——
`rowId` 失效的**已存在实例自动转 `orphan=true`**（等同 adopt 待遇：进 `OccupiedHard`、保留 Transform、info 条目列出），
条目动作 `[删除这 N 栋] [保留为固化] [改绑到指定行]`；默认保留（D-08-4 优先不删用户看得见东西）。
配套：06 §3.2 表校验新增检查项「存在引用已删行的实例」；`profileRowId` 永不复用（同 03 id 规则）。

### H-16（严重）「新建城 / 一键造城」与「重新生成」的语义必须分家
Route2 的「一键造城」被用户按了第二次。两个候选语义都能自圆其说：
① "重新生成"= 同参数再跑一次（保留人工层，即 D-08）→ 与 R1 的 A-7 一致；
② "新建一座城"= **清空人工层**换 seed 重来 → 会摧毁 R2-a 画的河与所有 adopt。
文档此前对这两个词**混用**（00 §5.2 只有「新建城」，01 §4.2 只有「重生成」）。
**裁决**：两个动作分离、命名与后果都不同，且 ② 为高危：
- `重新生成`（Rebuild）：只重算自动层，人工层原样叠回（A-7）。无需二次确认。
- `新建城`（New City）：新建空的意图层（或清空当前），**必须弹影响预览 + 列出将丢弃的人工层清单（河 N 条 / 固化 M 栋 / 锁区 K 块）+ 自动快照 + 需键入确认词**。
两按钮在主面板分列，不可合并（合并 = 迟早毁掉用户的东西）。

## 6. R3 —— 关掉编辑器再打开（跨会话 / 域重载）

前置：Rundeck 主线做完（T1~T4），场景已保存（建筑实例 + 场域 + 人工层资产 + Model 都在盘上），派生层按 D-13 **未落盘**。
现在重启 Unity / 触发一次域重载，然后**直接拖动那个 CBD 场域**。

| 推演点 | 结果 | 判定 |
|---|---|---|
| 打开场景后状态 | 意图层完整；`LandUseGrid`/parcel/slot/分裂栈/`prev` 快照全空 | 预期内 |
| S6 首跑（自动跟随触发） | 同 seed + 同意图 ⇒ 重算结果与盘上实例逐位相同（A-1）→ 理想情况应"认回"全部 GameObject | ⚠️ 见 H-10 |
| **认回依据** | 07 §3.3 的 diff **依赖 `prev` 内存快照**，而 `prev` 明确"关掉编辑器即失效" | ❌ **H-10 阻断** |
| Tracker 首帧 | 集合哈希基线为空 → 全部对象被当成差异 → 触发一次近全量重算 | ⚠️ 见 H-10b |
| 拉伸服务 | 域重载后 `Services` 清空 → 若 citymap 缓存了旧引用，`SetRepeat` 会打到失效对象 | ⚠️ 见 H-11 |

### H-10（**阻断级**）跨会话后 S6 无法认领已有实例 → 重复叠楼
`prev` 快照（slot→实例映射）是内存态，跨会话丢失。重新打开后 S6 若按"prev 为空"处理，会给每个 slot **新建实例**，
而盘上已有的那批（含 adopted/userModified）既不被识别也不被避让 →
结果：**同一地块两排楼叠在一起**，A-8 崩、A-7 崩、场景体积翻倍，且用户看不到任何报错（静默毁掉成果）。
这是 D-13（派生层不落盘）与"实例落盘"之间的接缝，R1 完全没走到（因为 R1 全程在同一会话内）。

**裁决：认回（reclaim）流程 —— 落盘实例与 slot 的映射靠 `CityBuildingTag` 反查，不靠内存快照**
```
S6 启动前先扫场景内所有带 CityBuildingTag 的实例，建 reclaim 表：slotId → instance（O(实例数)）
① tag.adopted || userModified || orphan || 属锁区 → 进"不可替换"集合，且其 footprint 烘焙 OccupiedHard；
② tag.rowId == 本次为同 slot 算出的行 且 位置一致 → 保留该实例（省一次 Instantiate，Preview 不闪）；
③ 不一致 → 销毁旧 + 新建（正常重排）；
④ slotId 在本次派生结果里不存在（地块已消失）→ 转 orphan（并入 H-15 的三选一处置）；
⑤ 未被任何 slot 认领、且无 tag 的场景物体 → 不碰（可能是用户自己的东西，绝不自动删）。
```
- `prev` 内存快照降级为**纯优化**（同会话内少扫一次），跨会话正确性完全由 tag 承担 → D-13 得以保持。
- 幂等性要求：重开后再存一次，场景不应多出一栋（验收 A-30）。
- H-10b：Tracker 首帧**建立基线而非触发重算**（把加载后的版本哈希记为"派生层记忆"），
  仅当认回表出现"未认领的 tag 实例"或版本对不上时才标脏（08 §5.1 补基线规则）。

### H-11（实现级）装配时序不能依赖"同一阶段"的顺序假设
06 §4.3 原文写"双方都在 `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` 里注册/取用"，
但 **不同程序集之间、以及程序集与场景加载之间，该回调的执行顺序不保证**。citymap 若在 stretch 之前跑 `TryGet`，
就永远拿到"降级"，而 stretch 其实完好——这正是 A-6-6 想测的东西，却会因顺序假象误判。
**裁决**：改为**惰性解析 + 不跨帧缓存**：
- `IStretchService` 在**首次需要时**解析（第一次落位带拉伸的建筑前），解析结果缓存并在**域重载时失效**；
- 面板显示"拉伸源"时实时 `Services.TryGet`，不用缓存值；
- 可用性由 false→true 的切换**不追溯重改已有实例**（只影响新实例），面板黄标列出"降级期间放置的 N 栋"，
  并提供显式「按 stretch 重建这些高度」动作；
- 注册仍须幂等（原 §4.3 的 error 风险不变，这是 M9 门禁项）。

### H-12（流程级，需用户批准节奏）改 core 必须两段式合并，且第一段可独立回滚
此前总纲 §6.4 只写了"要申报冲突"，没给出**怎么拆**。一次性提交"core+stretch+citymap"三段改动的问题是：
stretch 当时若有别的会话在改（R1 期间确实被 `ui-fix` 持锁），则该提交要么等锁、要么冲突，且失败时回滚面横跨三个包。
**裁决（两段式）**：
- **段 1**：只往 core 加一个纯新增文件（接口 + 无行为的枚举/结构），不改 core 任何既有 API、不碰另两个包
  → 编译风险≈0，门禁三项绿灯即交锁；此段合入后 citymap 走降级路径、stretch 无感知 → **两包都不阻塞**。
- **段 2**：待 stretch 空闲（取到 stretch 锁）再改其注册实现 + citymap 侧消费接线。
- 回滚成本：段 1 单删文件即可；段 2 若失败只回滚两包，core 接口留着无害（无实现=降级，已验证路径）。
- 若段 2 久等不到：功能不受阻（降级已可用），但 `Showcase` 演示视频必须录**段 2 完成后的效果**，否则 A-13 演示的是降级态。

### H-13（性能/内存级）批量拉伸会在落位循环里放大
`SetRepeat` 每次调用都会走 stretch 的 mesh 重建路径（SH 裁剪 + 顶点数组重分配，见 stretch DESIGN §4）。
07 §3.2 是"逐栋落位时拉伸" → 9000 栋 ⇒ 9000 次 mesh 重建与分配，且都在 Editor 主线程的 Commit 里。
R1 的 §6 性能预算（全量 ≤60s）没给拉伸留任何预算，这条会先炸。
**裁决**：
- 桥接接口增加**批量语义**（ADR-0001 定稿签名时并入）：`BeginBatch()/EndBatch()`（提供方内部合并分配与延迟重建）；
  提供方不支持批量时 citymap 侧兜底为"分帧摊销"（每帧预算 8ms，同 07 §6）；
- `IStretchService` 增加 `bool SupportsBatch { get; }`，面板据此提示性能档位；
- 目标：9000 栋的拉伸重建总耗时进全量预算（≤60s）内可完成，否则 §8 预算与 M9 联调清单同步修订。
- 注：此项属"core 接口签名扩项"，与总纲 R-13 同一处置通道（走 ADR + 用户批准）。

### H-14b / H-15b（并行面）注册唯一性与跨包引用检查
多 AI 场景下最可能出现的坏法：citymap 的某次会话为了让降级路径"能跑"而**顺手在 citymap 里注册了一个假实现**
→ 与 stretch 的真实现重复注册 → `Services` 保留先注册者 + `LogError` → 控制台门禁直接红。
**裁决**：M9 实施清单加两条硬检查（写进 06 §4.3）：
① 全项目 `Register<IStretchService>` **有且仅有一处**（在 stretch 包内）；
② citymap 永不注册该接口，只 `TryGet`；校验手段为提交前 grep 断言 + ACCEPTANCE 记证据。

# 第五轮（M1 实现自测，2026-11-03）

> 方法变化：前四轮是**纸面推演**，本轮是**代码 + EditMode 测试真实执行**（54 个用例跑在活编辑器里）。
> 这正是"推演只能发现设计缺陷，实现才能发现语义歧义"的分界。抓到 1 处实现缺陷 + 2 处文档/注释错误结论。

## 10. H-29（实现抓到的组合性缺陷，已修）

设计文档 08 §5.1 表末行写「adopted 建筑挪动 → **仅** OccupiedHard 重烘焙（旧+新 footprint）→**S3,S6 冲突复检**」。
实现时我把"复检 S3"直译成"置 `Road` 位"，于是 `Road` 的下游规则（`Parcel|Field|Building`）被连带触发
⇒ **挪一栋已固化的楼 = 重算地块**，恰好违反该行自己声明的"不得牵连"。

测试 `H29_OccupiedReloc_...` 首跑即失败（实际多出了 `Parcel` 位），当场暴露。

**修法**：`OccupiedReloc` 定义为**终端位**——`Expand` 对它不写任何传播规则，
由 `StageClaims` 让 S0/S3/S6 各自 `DependsOn` 直接认领它。撤销了我中途引入的多余 `Recheck` 位。

**沉淀为通用纪律**：文档里「→Sx 复检」这种写法，**不等于"置 Sx 的触发位"**。
复检某阶段要用只被该阶段认领的终端位，否则该位的下游规则会越权。这条适用于 08 §5.1 全表。

## 11. H-30（实现第二轮自测抓到：对象级单一 Kind 会让脏位归因错到不可见）

M1 首版接口是"每个意图对象一个 `Kind` + 一个 `manualVersion`"。但一个对象常承载**多种互不相干的可变面**：
`CityProject` 同时握着"世界参数（seed/尺寸/档位）"与"城心锚点"。它的 `Kind` 只能返回一个值（我写死 `WorldParam`），于是：

```
用户点「设为城心」 → TrySetCenterAnchor 只 bump 版本 → Tracker 读到 Kind=WorldParam
                  → DirtyOf ⇒ Seed|World ⇒ Expand ⇒ **All（全量重算）**
```

后果三层，且**都不报错**：① 城心变更绕过 `Center` 的近全链语义；
② **H-7 的修复被这条接线静默抵消**（城心重新变成"一动就全城重算"）；
③ 面板显示的脏位也是错的，用户看到的"将要重算什么"与实际发生的不符——比报错更糟。

**修法（接口契约级）**：变化不记在"对象"上，记在**通道（`IntentKind`）**上 —— `IntentChangeLedger`
持有 `List<(Kind, Sequence, Center, Size)>`，Tracker 按 `(对象 × 通道)` 粒度比对。`IntentKind` 同步改为 `[Flags]`
（同一对象一帧内可能多种变化，单值会互相覆盖），`DirtyOf` 从 `switch(kind)` 改为**逐位求并集**
（否则组合值落 `default` 返回 None = 静默丢脏）。

**必须序列化的原因**（这条同时补强了 H-9）：通道 `Sequence` 是 `[SerializeField]`。
Unity Undo 只还原序列化字段 ⇒ undo 后序列号回到旧值 ⇒ 与基线不等 ⇒ 标脏。
若账本用普通 C# 字段，undo 后序列号不变、Tracker 全瞎 —— 正是 H-9 的漏检形态，我首版就差点这么写。

守卫用例（新增 2 条，共 56 条全通过）：
`Channels_On_One_Object_Do_Not_Pollute_Each_Other`（城心提交不得推进 WorldParam 通道，反向同理）、
`Tracker_Dirties_On_Change_And_On_Value_Rollback`（首帧零重算 + 归因到 Center + 序列号回滚仍被感知）。

> 与 H-29 同源的方法论：**接口粒度不够时，缺陷不会崩，只会静默改变"重算什么"。**
> 凡"一个对象多个可变面"（本项目里遍地都是：表行 × 四维度、场域 × 几何与强度、记录 × 位置与 flags），
> 记账粒度必须到**面**，不能到对象。

## 19. H-37：`ampFactor` 只压低频，细节噪声完全绕过 `urbanFlatness`（违反 A-1-1）

**症状**：`flatness=0`（城内应"几乎全平"）时，城内标准差实测 **0.236m**，超出 A-1-1 规定的 **≤0.2m**。

**根因**（一行公式的括号位置）：
```csharp
heights[...] = ampFactor * amp * baseN + detailA * detail;   // 错：细节层没被 ampFactor 压
heights[...] = ampFactor * (amp * baseN + detailA * detail); // 对：压整条噪声和
```
细节层 `A=1.2m, λ=24m, 2 octaves` 单独就能贡献约 0.24m，所以 `flatness` 拖到 0 也压不住它。

**为什么纸面推演和首版测试都没抓到**：`urbanFlatness` 的语义是"城内有多平"，而我当时的心智模型是
"压掉**地形起伏**（=低频山形）"——把"细节纹理"当成不影响规划的东西而默认放过。但对用户来说，
鼠标在城里拖出来的地表**就是**微糙的，这就违反了 AGENTS §0.1「所见即所得」：旋钮看起来没生效。

**修法**：压幅系数作用于"低频 + 细节"的总和；同时把 A1_1 的断言从 `0.6f` 收紧到文档值 `0.2f`，
并补 **flatness=0.5 的线性断言**（`±6%`）——只测 0/1 两端会漏掉"中间段不跟手"这类缺陷。
修复后实测：`flatness=0` → **0m**（文档要求的 ≤0.2m），`flatness=1` → 0.813m。

**纪律**：**文档写了绝对数值，断言就必须用那个数值**，不得凭直觉放宽；
放宽的那一刻，实现就失去了一次被测试抓到的机会（H-37 是这条纪律的直接代价）。
另：旋钮类参数要测**单调/线性**，不能只测两端，否则"中间失效"的缺陷对用户不可见。

M2 的 28 条地形断言全部通过；ACCEPTANCE 已回填条目 21~28。

全绿复跑后我按 AGENTS §1.6b 取控制台实测数值写进 ACCEPTANCE，读数暴露了一处**文档硬数值违规**：

| 项 | A-1-1 文档口径 | H-37 前实得 | 修法后实得 |
|---|---|---|---|
| `flatness=0` 城内标准差 | **≤0.2m** | **0.236m（超 18%）** | **0m** |

**根因**：`TerrainBaseStage` 第 ③ 步写成 `ampFactor * amp * baseN + detailA * detail` ——

细节层单独就贡献约 0.24m，于是 `flatness=0` 时城内标准差被顶到 0.236m > 文档 0.2m。
